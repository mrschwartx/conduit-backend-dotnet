==================================================
2. API CONTRACT SUMMARY (openapi.yml is authoritative)
==================================================
General
- JSON only, camelCase, payloads wrapped in envelopes ({"user":...},
  {"article":...}, {"articles":[...],"articlesCount":n}, {"comment":...},
  {"comments":[...]}, {"profile":...}, {"tags":[...]}).
- Timestamps: UTC, ISO-8601 date-time (e.g. 2026-10-21T10:15:30.123Z).
- Authentication header: "Authorization: Token <jwt>"
  The scheme word is "Token", NOT "Bearer". Do not accept other schemes.
- Auth levels: REQUIRED (401 if missing/invalid), OPTIONAL (anonymous allowed;
  if a token is sent but invalid or expired -> 401), NONE.

Endpoints (all under /api/v1)
  POST   /users/login                       NONE      200  {user}
  POST   /users                             NONE      201  {user}
  GET    /user                              REQUIRED  200  {user}
  PUT    /user                              REQUIRED  200  {user}      (partial update)
  GET    /profiles/{username}               OPTIONAL  200  {profile}
  POST   /profiles/{username}/follow        REQUIRED  200  {profile}
  DELETE /profiles/{username}/follow        REQUIRED  200  {profile}
  GET    /articles                          OPTIONAL  200  {articles, articlesCount}
         query: tag, author, favorited, offset, limit
  POST   /articles                          REQUIRED  201  {article}
  GET    /articles/feed                     REQUIRED  200  {articles, articlesCount}
         query: offset, limit
  GET    /articles/{slug}                   OPTIONAL  200  {article}
  PUT    /articles/{slug}                   REQUIRED  200  {article}   (partial update)
  DELETE /articles/{slug}                   REQUIRED  204  no body
  GET    /articles/{slug}/comments          OPTIONAL  200  {comments}
  POST   /articles/{slug}/comments          REQUIRED  201  {comment}
  DELETE /articles/{slug}/comments/{id}     REQUIRED  204  no body
  POST   /articles/{slug}/favorite          REQUIRED  200  {article}
  DELETE /articles/{slug}/favorite          REQUIRED  200  {article}
  GET    /tags                              NONE      200  {tags}
Outside the versioned prefix:
  GET    /health                            NONE      200  plain text "OK"

Request envelopes: {"user":{...}}, {"article":{...}}, {"comment":{...}}.
Route matching: /articles/feed is a static route and must win over
/articles/{slug}. No article may ever be created with the slug "feed".

Error format (every non-2xx response, always JSON, except 204/health):
  { "errors": { "<field-or-resource>": ["message", ...] } }
Status codes
  400  malformed JSON body            errors.body = ["is not valid JSON"]
  401  missing/invalid/expired token  errors.token = ["is missing"] / ["is invalid"] / ["has expired"]
       wrong email or password        errors.credentials = ["are invalid"]   (login only)
  403  not the owner                  errors.article = ["forbidden"] / errors.comment = ["forbidden"]
  404  resource not found             errors.article = ["not found"] / profile / comment
  409  duplicate email or username    errors.email = ["has already been taken"] / errors.username = [...]
  415  request WITH a body but Content-Type is not application/json
  422  validation failure             errors.<field> = ["<message>", ...]  (all failing fields at once)
  500  unexpected                     errors.server = ["internal server error"]  (never leak stack traces)
Requests without a body (DELETE, follow, favorite) must NOT require a
Content-Type header.
Check order for protected endpoints: authentication (401) -> existence (404)
-> ownership (403) -> validation (422).


==================================================
3. BUSINESS RULES (identical in every backend)
==================================================
Field shapes
- User:    { email, token, username, bio, image }
- Profile: { username, bio, image, following }
- Article: { slug, title, description, body, tagList, createdAt, updatedAt,
             favorited, favoritesCount, author: Profile }
  In the list endpoints (/articles, /articles/feed) the article items OMIT "body".
- Comment: { id (integer), createdAt, updatedAt, body, author: Profile }
- bio and image: return null when not set. On input, null or "" clears them.
  Keys must always be present in responses (never omitted).
- token: a fresh JWT returned by POST /users, POST /users/login, GET /user, PUT /user.

Validation (trim whitespace first; count Unicode characters, not bytes)
- username: required, 3-30 chars, only [A-Za-z0-9_-]; unique case-insensitively
- email: required, valid email format; stored lowercase; unique case-insensitively
- password: required on register, minimum 8 chars (maximum 72 for bcrypt-safety)
- bio: maximum 300 chars
- image: empty/null, or a valid https URL
- title: required, max 100 | description: required, max 200 | body: required, max 20000
- tagList: max 10 tags after trimming and de-duplication; each tag 1-30 chars,
  no whitespace and no commas; keep first-seen order
- comment body: required, max 1000
- offset: integer >= 0 (default 0) | limit: integer >= 1 (default 20); values of
  limit above 50 are clamped to 50. Non-integer or out-of-range -> 422.
- Validation messages: short, human readable, e.g. "can't be blank",
  "is too short (minimum is 3 characters)", "is too long (maximum is 30 characters)",
  "is invalid". Report ALL failing fields in one 422.

Partial updates (PUT /user and PUT /articles/{slug})
- Field absent  -> unchanged. Field present -> validated and applied.
- "absent" and "null" must be distinguishable (bio/image null = clear).
- PUT /user: at least one field required, otherwise 422. Changing email or
  username re-checks uniqueness (409), ignoring the user's own record.
- PUT /articles/{slug}: only the author may update (403 otherwise).

Slugs
- Generated from the title: Unicode NFKD normalise, strip diacritics, lowercase,
  replace runs of non [a-z0-9] with "-", trim leading/trailing "-", max 80 chars,
  fallback "article" if empty.
- Uniqueness: on collision append -2, -3, ... until free.
- Reserved: "feed" (treat as taken, so the title "Feed" becomes "feed-2").
- When the title changes on update, regenerate the slug (excluding the article's
  own current slug from the collision check). If the title is unchanged, keep the slug.

Behaviour
- Article lists are ordered newest first (createdAt desc, then id desc).
- GET /articles filters: tag (exact match), author (username), favorited
  (username). Unknown author or favorited user -> 200 with empty list, NOT 404.
  Filters combine with AND. articlesCount is the total matches ignoring offset/limit.
- GET /articles/feed: only articles by authors the caller follows.
- favorited / following are computed relative to the caller; anonymous = false.
- favoritesCount = number of users who favorited the article.
- Follow, unfollow, favorite, unfavorite are idempotent and always return the
  updated resource. Following yourself -> 422 errors.username = ["you cannot follow yourself"].
- GET /tags: the 20 most used tags, ordered by usage desc then alphabetically.
- Comments: newest first. Only the comment author can delete (403). A comment id
  that does not belong to the given slug -> 404. Comment ids are integers.
- Deleting an article also deletes its comments and favorites.
- Passwords are stored only as a salted slow hash (bcrypt or argon2). Never
  return or log a password or hash.
- Login by email (case-insensitive). Same 401 for unknown email and wrong password.

4. NON-FUNCTIONAL REQUIREMENTS (all backends)
==================================================
Configuration (environment variables, 12-factor, with sensible dev defaults)
  PORT=8080
  DATABASE_*             connection settings for the stack's database
  JWT_SECRET             required, min 32 chars, fail fast at startup if missing/short
  JWT_TTL_MINUTES=720
  CORS_ALLOWED_ORIGINS=http://localhost:5173
  LOG_LEVEL=info
  Provide a .env.example. Never commit real secrets.

JWT
- HS256. Claims: sub (user id as string), username, iat, exp.
- Verify signature and expiry on every request that carries a token.

Security
- Parameterised queries only. No string-built SQL/query documents.
- CORS restricted to CORS_ALLOWED_ORIGINS; allow the Authorization and
  Content-Type headers and the methods used by the contract.
- Add basic security headers (X-Content-Type-Options: nosniff, etc.).
- Limit request body size (e.g. 1 MB).
- Do not reveal whether an email exists (see login rule). Error responses never
  contain stack traces or SQL.

Logging
- Structured (JSON) logs to stdout, level from LOG_LEVEL.
- One access-log line per request: method, path, status, duration, request id.
- Generate or propagate X-Request-Id and include it in every log line and
  in the response header.
- Log unexpected errors with stack trace server-side only.
- Never log passwords, hashes, JWTs or the Authorization header.

Other
- Graceful shutdown. GET /health outside /api/v1.
- Database schema created by versioned migrations (or explicit index setup for
  MongoDB), not by ad-hoc auto-DDL at runtime.
- Avoid N+1 queries when assembling article/comment lists with author profile,
  favorited and favoritesCount.


==================================================
5. .NET-SPECIFIC REQUIREMENTS
==================================================
Solution layout
  src/Conduit.Api              (Program.cs, controllers, DTOs, middleware, config)
  src/Conduit.Application      (services, validators, abstractions)
  src/Conduit.Domain           (entities, rules)
  src/Conduit.Infrastructure   (EF Core DbContext, configurations, migrations, JWT, hashing)
  tests/Conduit.Tests
Organise by feature inside each project (Identity, Profiles, Articles, Comments).
Do not expose EF entities from controllers. Keep controllers thin.

Routing
- Everything under /api/v1 (route prefix or UsePathBase; choose one, verify that
  it behaves correctly with routing, auth and Swagger/OpenAPI if used) and
  /health outside it. Make sure /articles/feed is not captured by /articles/{slug}
  (static literal routes win, add a test).

Auth
- The scheme is "Token", not "Bearer". Use JwtBearer with
  JwtBearerEvents.OnMessageReceived reading "Authorization: Token <jwt>", or a
  small custom AuthenticationHandler. Reject other schemes.
- Required endpoints use [Authorize]; OPTIONAL endpoints are anonymous but must
  still authenticate when a token is present and return 401 when a present token
  is invalid (a custom handler or middleware makes this easiest).
- OnChallenge / OnForbidden must write the contract error JSON.

Errors and validation
- Override ApiBehaviorOptions.InvalidModelStateResponseFactory and add a global
  IExceptionHandler so EVERY error is {"errors":{field:[msgs]}} with contract
  status codes. No ProblemDetails or default ASP.NET error bodies may escape,
  including 400 for malformed JSON, 404 for unknown routes, 415, and 500.
- Run FluentValidation explicitly in a filter or service and return 422 with all
  failing fields; use camelCase property names as keys.
- System.Text.Json: camelCase, ISO-8601 UTC, and nulls for bio/image must be
  WRITTEN (do not set DefaultIgnoreCondition = WhenWritingNull globally).
- Partial updates: absent vs null must be distinguishable. Use JsonElement /
  JsonNode, or an Optional<T> wrapper with a JsonConverter, for the update DTOs.
- Map SqlException unique-violation numbers (2601/2627) to 409.

EF Core / SQL Server
- nvarchar columns, datetime2 in UTC, unique indexes on lower-cased email and on
  username with a case-insensitive collation, unique index on slug. Comment id is
  a bigint/int IDENTITY.
- SQL Server rejects multiple cascade paths: configure delete behaviour
  carefully (e.g. NoAction + explicit deletion in the article-delete service,
  inside one transaction) so deleting an article removes its comments and favorites.
- Use AsNoTracking for reads, projections (Select) and batched queries to avoid
  N+1 for author profile, favorited, favoritesCount and following flags.
- Popular tags and filters (tag/author/favorited/feed) computed in the database.
- Migrations checked in; apply them on startup only in Development, otherwise
  via an explicit command documented in the README.

Logging: Serilog with request logging middleware, enrichers for X-Request-Id,
JSON output, level from LOG_LEVEL.

Tests: unit tests for validators/slugs; integration tests with
WebApplicationFactory + Testcontainers MsSql exercising the real HTTP pipeline.

   versions, and verify framework APIs against official documentation instead
